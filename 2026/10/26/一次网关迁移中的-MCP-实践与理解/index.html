一次网关迁移中的 MCP 实践与理解

一次网关迁移中的 MCP 实践与理解

Ingress Nginx 退役 的消息去年（2025）就出了，我们就在考虑公司网关的迁移方案。Kubernetes 对于网关下一代的设计是 Gateway API，恰好阿里云的公众号也经常发布关于 Higress 开源产品的内容，声称其不仅是传统微服务网关，也是新时代的 AI 网关（对于 MCP 协议的更新支持很快），从 ingress-nginx 迁移也很方便（同时支持 Ingress 和 GateWay API），基于此我就尝试把原有的路由修改到 higress 上。

在 k8s 上部署服务并不是难事，如果服务器能直接连接外网，使用 helm 下载简单配置并运行即可；即使不能连接外网，load 加载指定版本镜像，写 yaml 创建 ns、sts、deploy 也是可以的。

不过这些不是本篇内容的重点，部署好 higress 后，我发现貌似还是需要我进 higress-console 对应的 web 页面添加路由。

我司服务器集群的 ns 都有几十个，只考虑基础的每个 ns 里 web 和 gateway 两个 svc，也需要我创建几十条路由，更别提还有一些额外的情况：如音视频服务需要 websocket，xxl-job 等独立服务也需要暴露端口访问。

于是我就找有没有更简单的方案，发现有人去年写了一个 higress-ops-mcp-server 的项目，项目使用 fastmcp 封装了对于 higress 中路由、服务的基本操作，并用 langchain 创建出 agent 支持用户使用自然语言对 higress 进行操作。

MCP 是什么

MCP 解决了AI系统面临的一个根本问题：数据孤岛。即使最先进的AI模型也受限于与外部数据的隔离，难以访问存储在内容库、业务工具和开发环境中的信息。MCP提供了一个统一的协议，替代了分散的集成方式，使AI系统能够更简单、更可靠地访问所需数据。

举个例子：用户问 Agent 我这个项目的 Redis 集群里是否存在 bigkey，Agent 没办法直接连 redis，它会给出一些方案，比如执行下 keys user* 把返回结果贴回来等等，或者用户把 redis 的 host、username、password 给 Agent，Agent 自己写 py 脚本去连接。总之 Agent 获取外部系统信息的手段有限，MCP 可以让 Agent 访问外部的系统。

MCP 里有 Host、Server、Client 几个核心部分，Host 是 Agent 应用本体（Claude、WorkBuddy等），Server 则是指提供能力的外部程序，Client 是 Host 内部维护的与 MCP Server 的连接。Server 本身具备管理资源的能力，Host 通过内部的 Client 跟 Server 通信，Server 根据通信内容操作 Resource。

我们常说的 Stdio、Streamable HTTP 则是指 Client 和 Server 通信的方式。

看代码其实和我们正常调用一个三方平台的方式（或者 Function Calling）一样，为什么还要多此一举用 MCP 封装呢？

我认为有以下原因：

  1. 易维护，可移植，可复用：MCP 是 Agent 业界规范，Claude 换 Codex、Hermes 都可以兼容，而且如果有其它平台需要对接 Higress，可以复用而无需维护多处；
  2. 解耦：MCP 解决的是 Agent 如何发现、连接、执行工具的问题，而 Function Calling 解决的是 Agent 如何表达它需要进行工具调用的问题（输出一个 json 表达要调用的工具和参数）。从这个层面看 MCP 更像是 Function Calling 的下游，单独使用 MCP 解耦了 Agent 和业务平台。

有的人可能以为 Stdio 和 Streamable HTTP 是 Server 和 Resource 的通信方式，其实不然，这是 MCP Client 和 MCP Server 的通信方式，中间还有过 SSE 方式，由于不符合传统 请求/响应 的共识（两个端点，一个端点接收消息返回请求已接收，但响应是从 SSE 长连接返回的。传统的都是发请求返回本次请求的响应内容）而且不利于服务提供方的水平拓展（需要粘性会话，因为维持了 SSE 长连接），目前已经舍弃了。
