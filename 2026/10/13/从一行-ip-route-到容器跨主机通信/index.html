从一行 ip route 到容器跨主机通信

从一行 ip route 到容器跨主机通信

我使用 docker、k8s 已经有一些时间了，业务也几乎都使用容器部署，但对容器网络一直知之甚少，网络本身也是个较为复杂的内容。

从云计算转 Java 开发近三年，近日发现现在的实践和之前的记忆已经有些偏差了，如 Endpoint-> EndpointSlice、ingress-nginx 停止维护等等等等，于是新搭建了个 k8s 环境顺便学习下容器网络的知识。

ip rule

ip rule 按照优先级决定包去哪个 table 里找路由信息

格式为：[优先级]: [匹配条件] [动作]

字段 含义
第一列数字 优先级，数字越小越优先(0 最先看)
from all 匹配条件：所有包
lookup local 动作，查 local 表(本机 IP、广播地址专用)
lookup main 动作，查 main 表(平时 ip route 看到的就是它)
lookup default 动作，查 default 表(一般为空,保底用)

操作系统决定一个包发往的下一个地址的流程大致如下：

  1. 按 rule 优先级从小到大遍历 ip rule。
  2. 对每条 rule，先看选择器是否匹配，比如 from all、from 10.0.0.0/8、fwmark 1 等。
  3. 如果匹配，就执行动作。最常见动作是 lookup <table>。
  4. 去指定 table 里做路由查找：
    • 先最长前缀匹配；
    • 同前缀再比 metric 等。
  5. 如果在这张表里找到了路由，就用它，停止继续查后面的 rule。
  6. 如果在这张表里没找到路由，就继续下一条 rule。
  7. 如果动作是 blackhole、unreachable、prohibit，则直接返回对应结果，不再继续。
  8. 所有 rule 都走完还没找到，就返回网络不可达。

默认情况下 linux 上只有这 3 个规则，与有多少个网卡无关。自定义规则通常会落在 0～32766 之间，从而覆盖默认行为。

ip route

ip rule 的返回结果是按照优先级去哪个表里查, 如动作里的 lookup main 代表去查询 main 表：

main 表是 ip route 指令默认的 table, 上述指令等价于 ip route

字段 含义
default via 192.168.176.1 如果没有更具体的匹配,就发给 192.168.176.1 这台设备
172.17.0.0/16 dev docker0 发往 172.17.0.0/16 这个网段的包,从 docker0 网卡出去
dev docker0 Docker 安装时创建的虚拟网卡,172.17.0.0/16 是它的网段
proto kernel 这条路由是内核根据本机网卡 IP 自动生成的，也可能出现 proto dhcp 表示 DHCP 协议自动分配来的
scope link 目的地跟本机是同一链路(同一网段)
src 172.17.0.1 出去时用 172.17.0.1 作为源 IP

network namespace

Linux 中有 NameSpace （命名空间）的技术，在许多的框架里也有体现：k8s、nacos、rabbitmq，ns 之间的内容相互隔离，那么 Network NameSpace 的作用也就显而易见了，在这个 ns 下的网络配置（网卡、路由表、ARP 表、iptables 规则）是独立的。

通过 exec test netns 的输出可知：netns 里看不到主机的网卡、路由规则。本机执行相关指令，也看不到 netns 内的网络设备，两边的世界是隔离的。那双方怎么通信呢？

veth pair

解决方案是 veth pair(虚拟以太网对)，其特点如下：

  • 有两个端点，数据从一端进入一定从另一端出来；
  • 两端可以被各自赋 IP、参与路由；

那么主机与 netns 内进程通信的解决方案就出来了：为 netns 创建一个 veth pair，一头在 netns 里，一头在主机上，这样 netns 就可以跟外界通信了。

netns 创建时 lo 设备默认是 DOWN 状态（可以回看上文的 ip netns exec test ip addr 输出）。如果要在 netns 内跑需要”本机回环”才能正常工作的服务（比如很多 health 检测脚本会 curl 127.0.0.1），记得手动 ip netns exec <ns> ip link set lo up。

container

container（容器）的本质其实是进程。

进程的定义非常多种多样，一个简单的定义是：进程是程序的动态执行。程序是代码或其产物（如二进制文件），静静的躺在磁盘上。而进程是程序被执行起来的样子：内存中的数据、寄存器里的值、堆栈和被打开的文件等这些数据和状态的总和就是进程。

容器通过约束和修改进程的动态表现，为其创造出一个”边界”。其核心原理一个是前面介绍过的 NameSpace 技术，除了 network ns，linux 还提供了 pid、mount、uts、user 多种 ns，这是 linux 创建新进程的一个可选参数；另一个核心原理则是 Cgroups，既然容器是一个进程，自然会与系统的任何其他进程一起争抢资源，Cgroups 提供了限制进程能使用的资源（cpu、mem、blkio）上限的能力。

所以一个进程运行在一个 netns 里，前面的内容实现了 netns 与主机的通信，也就是只要为每一个容器创建一个 veth 设备，容器与主机就可以通信了。

那么容器与容器之间如何通信呢？

一个简单的方案是，如果容器A需要与容器B通信，那么容器A和容器B间也添加一个 veth 设备，仔细想一下其实问题很多：如果互相通信的容器有 N个，那么需要 N(N-1)/2 个 veth 设备，根本不可行。

现实生活中，只要我们的设备连同一个路由器，互相之间就能通信，这里也是同理。

bridge

首先介绍一下交换机和路由器，交换机是二层设备，工作在数据链路层，会根据收到包的 MAC 地址转发给对应的主机；路由器是三层设备，工作在网络层，能根据收到包的 IP 地址决定从哪个网卡转发出去。

bridge 就是让所有 veth 都接到一个虚拟交换机上，这样互相之间就可以通信了，N 个容器只需要 N 个 veth。

大名鼎鼎的 docker0 就是一个 bridge。严格地说是一台二层交换机——它只会按 MAC 学习、转发同网段内的帧，并不会在不同 IP 网段之间路由包。所以光有 bridge 是不够的。

解决这个问题的方案分两步：

  1. 给 bridge 本身赋一个 IP，让它”接入协议栈”：能查本机路由表、接收”目的 IP 是自己”的包、能从自己的视角看邻居表。
  2. **打开 /proc/sys/net/ipv4/ip_forward=1**，允许内核把”目的 IP 不是自己”的包继续向外转发。

只有这两步都做了，bridge 才同时是一台 L2 交换机和一台 L3 路由器——容器之间同网段通信走 L2，容器对外网通信走 L3 转发。

小结

容器网络并不是黑盒，整个文章其实就讲了 4 件事:

  1. 路由决策(ip rule + ip route)：内核拿到一个 IP 包,先按优先级选路由表,再在表内做最长前缀匹配,得到”下一跳 + 出接口”。
  2. Network Namespace：把网卡、路由表、iptables 隔离开，让进程拥有自己独立的网络栈；veth pair 就像一根”虚拟网线”, 把两个 ns 串起来。
  3. Linux Bridge：虚拟的 L2 交换机，把”网线”的一端统一收口在一台设备上，实现 N 个 ns 之间两两通信。
  4. 三层转发 + NAT：bridge 被赋 IP + ip_forward=1 就升级成”带路由功能的小交换机”；iptables MASQUERADE 把容器源 IP 翻译成 eth0 的出网 IP，容器就真正”能上网”。

Kubernetes 里的 CNI、那么多的网络实现 flannel、calico 等其实也是这些事情的不同拼装。
