TDengine : error code 8984, Timeout waiting for connection from pool

TDengine : error code 8984, Timeout waiting for connection from pool

环境：Spring Boot 3 + taos-jdbcdriver 3.8.0(RESTful jdbc:TAOS-RS://)+ HikariCP
现象：时序服务 (MQ 消费 → 虚拟线程并发写 TDengine) 报错

项目中有一个时序服务，连接了单机版 TDengine，用的是 REST 连接方式(jdbc:TAOS-RS)。

项目用了 JDK21，而写数据库多为 IO 任务，用虚拟线程池很合适，所以内部逻辑为消费者消费 MQ 里的数据生成待执行的 SQL 丢到虚拟线程池里，线程池执行完任务后根据结果更新数据库记录状态。

现象

近期由于一些原因经常需要源平台补推数据，补推时频繁报错:

这个 SQL 很长，但是语法绝对正确，复制出来单独执行是成功的。而且平时正常推送分钟级数据时几乎不会出现，只有补推这样瞬时产生很多数据的时候才会出现。TDengine 服务器资源也无压力，cpu、 内存使用均不超过 30%。

看到 Timeout waiting for connection from pool 第一反应往往是:连接池不够大 → 去调 HikariCP。

但是调大后依然报错。 最后发现这个”池”根本不是 Hikari 的池。

排查过程

我认为的疑点是: 报错形态不像 Hikari 超时

HikariCP 拿不到连接时抛的是:

而实际报错是 error code [8984] (0x2318),错误信息只有一句Timeout waiting for connection from pool——这是 Apache HttpClient 的ConnectionPoolTimeoutException 标准文案。也就是说: 排队发生在 HttpClient 的连接管理器里, 而不是 Hikari。

官方文档 里对该错误码的解释是：REST 连接中出现了数据传输异常，请检查网络情况并重试。

所以这个错误应该是驱动包自己定义的，接下来解包驱动 jar 定位错误码，对本地 Maven 仓库的 taos-jdbcdriver-3.8.0.jar 解包反编译:

8984 是驱动自己定义的错误号, 对应 RESTful 客户端 IO 异常——驱动执行 HTTP 请求时把底层 IOException(含连接池租借超时)统一包装成 8984。和 Hikari 无关。

关键内容:

  • httpClient 是 static volatile，通过双重检查锁实现单例，进程内所有 RestfulConnection 共享同一个 PoolingHttpClientConnectionManager。也就是说 Hikari 开 400 个 JDBC 连接，但底层 HTTP 请求依然全挤这一个池。
  • **默认 httpPoolSize = 20**，同时作为 maxPerRoute 生效:

所谓的”路由” = 目标 host:port。 单实例 taosAdapter 部署下,所有请求都发往192.168.41.190:6041，属于同一条 route。

而在业务侧消费链路:

200 个并发虚拟线程 > 20 个可用 HTTP 连接 → 180 个请求在池前排队等 lease。

再看驱动里请求级 RequestConfig 的构造（执行时真正获取 request）:

等池超时被硬编码为 1000ms，排队超过直接抛ConnectionPoolTimeoutException: Timeout waiting for connection from pool。即使有默认的重试(每次仍要排队)，高并发下仍然大面积失败。

所以问题的根因就是：TDengine 单 route 下默认连接数为 20，正常情况下消费还跟得上，但高并发下明显不足。
